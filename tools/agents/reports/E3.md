## Evidências de que o referente é `char` mutável

1. **Grafia keel da spec.** `keel-spec.md:668` escreve o texto como
   `slice const char text;`. Os exemplos do backend escrevem `buffer slice char
   lines;` (linha 444), `void (*g)(slice char s);` (701) e `[[maybe_unused]]
   slice char s;` (749), todos sem `const`. O mapeamento da linha 113 também tem
   `buffer const char → keel_buffer_const_char` como entrada separada.
2. **Código do cgen.** `tools/cgen/gen/keel/keel_slice_char.h` existe, gerado pelo
   `transform` (`tools/transform/base/Makefile:18-19`, `-t $$T` produz
   `keel_slice_$T`). `tools/cgen/src/engine/ast.c` e `tools/cgen/src/tool/tool.h`
   usam `keel_slice_char`. Não há `keel_slice_const_char` em `tools/cgen/src`.
   Trocar nos documentos de design do cgen os descreveria com um tipo que o
   código não tem.
3. **Texto do próprio lexer-design.** `design/lexer-design.md:60` diz que
   `keel_slice_char` usa `char *` no C gerado e que uma futura instância
   `slice const char` só reforçaria o contrato. Trocar só o nome deixaria a frase
   falsa (`keel_slice_const_char usa char *`).
4. **Golden.** O golden tem `keel_slice_const_char` (`{ size_t len; const char
   *ptr; }`) e nenhum `keel_slice_char`. Não há `keel_buffer_keel_slice_const_char`
   nem `keel_buffer_slice_char` no golden, então o derivado do backend (linhas
   449-456) não tem prova no golden.

## Incoerências encontradas (não corrigidas)

- `keel-c-backend.md:450`: `typedef struct keel_slice_char keel_slice_char;` é
  uma forward typedef. O golden define o struct completo no `.type.h`
  (`typedef struct keel_slice_const_char { size_t len; const char *ptr; }`). O
  trecho não mostra o layout real.
- `keel-c-backend.md:113` e `:896` usam `keel_buffer_slice_char` /
  `keel_buffer_slice_char_ptr`, enquanto a linha 449 usa
  `keel_buffer_keel_slice_char`. Os dois nomes não coincidem entre si.
- `design/lexer-design.md:60`: a frase "uma futura instância `slice const char`"
  já está desatualizada se a fonte de verdade for o golden.

## Decisão pendente (André ou Opus)

Duas saídas, e o cartão precisa escolher uma antes de qualquer troca:

- **A. Manter `char` mutável.** Os documentos de design e os exemplos do
  backend continuam com `keel_slice_char` e `slice char`, que descrevem o que o
  código faz hoje. Então o E3 vira só a correção de `lexer-design.md:60` (e do
  `keel_buffer_slice_char` na linha 113), sem troca em massa.
- **B. Texto constante na spec.** Trocar na keel-c-backend os exemplos de texto
  (`slice char` → `slice const char` e `keel_slice_char` → `keel_slice_const_char`),
  e manter `keel_slice_char` nos documentos de design do cgen, porque o código do
  cgen é `char *`. Isso exige um cartão separado, porque o backend ficaria
  diferente do cgen. Também pede decisão sobre a grafia keel dos exemplos.
